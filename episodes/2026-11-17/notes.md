# Notes 2026-11-17

## News

### 1. Google catches the first fully autonomous exploit pipeline in the wild: "exploit_agent"
- Why it matters for Lucas: The patch-diff-to-exploit loop is now automated end to end, so the time between a public patch and an attack against an unpatched system shrinks toward zero. That matters for anything he self-hosts (WordPress sites, RAG front-ends, MCP servers), and the attacker uses the same multi-agent pattern he builds with, just pointed the other way.
- Facts:
  - Google's Threat Intelligence Group (GTIG) says it "identified threat actors using LLM frameworks to fully automate vulnerability discovery and exploitation without a human in the loop for the first time." [primary] (https://cloud.google.com/blog/topics/threat-intelligence/agentic-threat-activity-crosses-a-significant-threshold)
  - GTIG describes exploit_agent as "a multi-agent vulnerability research and weaponization framework" that integrates with "multiple frontier and local LLMs". It runs continuous differential analysis of popular web application software: it compares code before and after patch announcements, identifies likely vulnerabilities, drafts exploits and executes them automatically. [primary] (same URL)
  - GTIG found it on an exposed staging server. Victim telemetry pointed to French websites in media and entertainment and in the education sector. One example in the report is an insecure capability check in the Ultimate Addons for Gutenberg (Spectra) WordPress plugin, version 2.19.25. [primary] (same URL)
  - The framework also shipped post-compromise scripts for internal reconnaissance, brute-forcing, installing webshells and removing other attackers' webshells. [primary] (same URL)
  - The Decoder reports that Russian-language comments in the configuration files suggest a Russian-speaking operator. [secondary] (https://the-decoder.com/google-warns-that-fully-automated-cyberattacks-have-arrived-and-will-get-worse-fast/)
  - GTIG's assessment is that these tools "currently trade stealth for velocity": unrestricted autonomous execution "generates forensic traffic, relies on recognizable identifiers, and leaves behind distinct code-level traces". GTIG expects future versions to need less human involvement and to get stealthier. [primary] (GTIG URL)
  - GTIG places exploit_agent in a wider ecosystem of open-source offensive agent frameworks, including CAIRN, CyberStrikeAI, PentAGI and HexStrike AI, the last of which it describes as an MCP-integrated harness. [primary] (GTIG URL)
- Skeptic angle / open questions: This is one operator on one exposed server. GTIG does not say how many exploits actually succeeded or which models did the work. "First time" means first time GTIG observed it. The useful takeaway for defenders is the window GTIG describes, where these attacks are fast but noisy and therefore detectable. The thing to watch is how long that window stays open.
- Mia hook: "I asked an agent to diff two releases of a plugin I use and tell me what the patch fixed. It took about four minutes. That's the first half of this attack. How long between `git tag` and exploit when nobody is in the loop?"

### 2. OpenAI opens its internals to four outside safety assessors (Apollo, METR, Transluce, Goodfire)
- Why it matters for Lucas: This is third-party evaluation of exactly what he cares about: monitors, safeguards, and whether agents undermine the checks placed on them. The publication terms show where the line falls between real independence and audit theatre, and that question applies just as much to his own "who checks the agent" design. It follows on from the 2026-10-24 deep dive on trajectory monitors.
- Facts:
  - OpenAI announced a "first phase of embedded assessments" with Apollo Research, METR, Transluce and Goodfire to independently evaluate model alignment, safeguards and monitoring systems. [secondary] (https://openai.com/index/our-first-phase-of-embedded-assessments)
  - METR will assess misaligned behaviour in OpenAI's largest reinforcement-learning run to date, including failures that existing tests and monitors may have missed. OpenAI says it expects this to lead to longer-term, continuous embedded engagements on its "most load bearing safety claims and safety cases". [secondary] (https://openai.com/index/our-first-phase-of-embedded-assessments/, via search snippet)
  - Apollo: a four-month assessment of whether models undermine safeguards in themselves or their successors, with access to training code, datasets, RL rollouts with reasoning traces and intermediate checkpoints. Two public reports are planned. OpenAI may redact supporting evidence but not verdicts or unfavourable results. Unredacted reports go to the board's Safety and Security Committee. [secondary] (https://casrai.org/news/openai-embedded-assessments-apollo-metr-2026)
  - Transluce: a six-week pilot reviewing selected internal post-training alignment evaluations, with a follow-on planned for early 2027. Its access is explicitly not equivalent to employee-level access, and it cannot publish results on internal-only models. Goodfire will use interpretability methods to study model internals. [secondary] (same CASRAI URL)
  - Context: in an earlier pilot, METR and Redwood Research spent time inside OpenAI reviewing its agent-monitoring systems and found new vulnerabilities, including an exploit agents could have used to keep hundreds of their actions from being monitored. [secondary] (https://finimize.com/content/outside-researchers-found-gaps-in-openais-ai-agent-monitoring)
- Skeptic angle / open questions: OpenAI decides the scope ("access tied to agreed claims") and can withhold access for security or IP reasons. Earlier external assessments got days, not weeks: Apollo reportedly had three days on GPT-6 Astra, two of them with chain-of-thought access (https://aiweekly.co/alerts/verge-metr-apollo-got-days-not-weeks-for-openai-safety-audits) [secondary]. Things to watch: whether the Apollo reports appear on time, how much evidence is redacted, and whether METR's monitor-assessment scope gets agreed at all, since it is still under negotiation.
- Mia hook: "'You can redact the evidence but not the verdict.' Is a verdict without evidence worth anything? Or is that exactly the trade-off I make when I let one agent grade another and only read the summary?"

### 3. Qwen4-Max: frontier-adjacent at $1.50/$4.50, but the Max weights stay closed
- Why it matters for Lucas: Qwen4-Max is a cheap, long-context agent model that can be called over an OpenAI-compatible API. It also ends an expectation: Alibaba open-weighted Qwen3.8-Max in August but is not doing the same for Qwen4-Max. Anyone planning local or self-hosted work on Qwen should plan around the smaller Qwen4 models, which have been promised but not dated.
- Facts:
  - General release on 16 November 2026, after a preview from 11 November. [secondary] (https://www.datacamp.com/blog/qwen4-max)
  - 2.4 trillion backbone parameters, 71 billion active per token, plus a 328-billion-parameter N-gram embedding. 1M-token context window. [secondary] (https://the-decoder.com/alibabas-qwen4-max-takes-on-opus-5-5-gpt-6-and-kimi-k3-1-pro-at-much-lower-prices/; https://www.datacamp.com/blog/qwen4-max)
  - Architecture: hybrid attention where Gated DeltaNet layers compress earlier context into a fixed-size state and Qwen Sparse Attention layers retrieve exact details on demand (a 3:1 ratio according to The Decoder). Also a "Gated Residual" with four parallel paths per layer, and N-gram embedding lookup tables. [secondary] (same URLs)
  - Price on QwenCloud: $1.50 per million input tokens, $4.50 per million output tokens, $0.075 per million cached tokens. [secondary] (https://www.datacamp.com/blog/qwen4-max; The Decoder)
  - 43 points on the Artificial Analysis Intelligence Index v5.0.1, second among Chinese models behind Kimi K3.1 Pro (46). Cost per index task: $3.27, against $10.02 for Qwen3.8-Max. [secondary] (The Decoder)
  - Strengths and weaknesses: 46.7 on Agents' Last Exam v1.1 (Opus 5.5: 43.4), but 48.5 on Terminal-Bench 4.0 (Kimi K3.1 Pro: 67.2) and 31.5 on ProgramBench (Opus 5.5: 65.0). [secondary] (https://www.datacamp.com/blog/qwen4-max)
  - Closed weights. Alibaba says smaller Qwen4 models will be released as open source later, without naming sizes or dates. [secondary] (https://www.datacamp.com/blog/qwen4-max; https://www.digitaltrends.com/computing/qwen-4-max-aliababas-latest-flagship-ai-model-announced/)
  - By contrast, Alibaba released the weights of Qwen3.8-Max (Qwen3.8-2.4T-A95B) on 13 August 2026. [secondary] (https://rits.shanghai.nyu.edu/ai/qwen3-8-2-4t-a95b-alibaba-open-weights-its-max-tier-flagship/)
- Skeptic angle / open questions: Most benchmark numbers are Alibaba's own and come through aggregators. The profile is lopsided: strong on agentic exams and legal, weak on coding. On r/LocalLLaMA the debate is whether Qwen 4 is the last open generation; Alibaba's commitment to smaller open models is the counter-evidence, but it has no dates. A data-residency point for Dutch or EU use: the free quota mentioned is tied to the Singapore region.
- Mia hook: "I ran my RAG eval on Qwen3.8 locally because the weights existed. Do I now re-run it against an API I can't pin a version of? And does the 1M context replace my retriever, or just make the bill longer?"

### 4. AI and the two margins of work: why job losses show up before job creation (arXiv, Esposito & Zhang)
- Why it matters for Lucas: The paper is about measurement as much as AI. It argues that payroll statistics capture displacement at incumbents quickly but capture new-activity creation late, so "no effect yet" and "J-curve under way" look the same in today's data. It also proposes a statistic, the net reinstatement ratio, that a CPB-style institute could actually build.
- Facts:
  - Authors: Mark Esposito (micro1 and Northeastern University) and Liu Zhang (micro1). arXiv 2611.17530, November 2026. [primary] (https://arxiv.org/pdf/2611.17530v1)
  - Computing-era evidence (Census BDS): firms entering in 1978 or later grew from 2.55 million to 45.68 million employees by 1998, while pre-1978 firms lost 5.69 million. The later entrants held 42.4% of payroll employment by 1998. Entering cohorts kept about 80% of initial payroll after five years (95% interval 77.35–82.63%). [primary] (same)
  - Over 1982–1998, entrants added an average of 2.78 million payroll jobs a year, young incumbents (ages 1–5) contributed −0.44 million and older incumbents −0.52 million. [primary] (same)
  - Across 84 industries, one standard deviation of automation-patent exposure was associated with 4.95 points less incumbent employment by 1982 (SE 1.84). By 1998 the gradients were −9.39 for incumbents and +5.94 for entrants, but with standard errors of 6.57 and 7.17. The authors call the later entrant build-up "suggestive rather than precise". [primary] (same)
  - Model: one AI capability lowers the cost of acceptable output in existing production and also makes new projects worth attempting. Founder effort is modelled separately from hired hours. A sudden 50% efficiency gain with slow incumbent re-scaling cuts hired hours by 4.58% on impact. The same gain diffusing over about seven years produces a trough of 0.23% near year 3.8, recovery around year 6.8, and +0.32% by year 15. [primary] (same)
  - AI-era data (BLS establishment data, 72 industries, 2022Q4–2026Q1): industries one SD more exposed to LLMs lost 14.7% of 2019 employment at continuing establishments, against 12.5% for one SD less exposed. The difference is 1.1 points with SE 1.9, so there is no gradient. Openings more than replaced these losses. [primary] (same)
  - The authors say plainly that this null "is also what no effect on payroll would look like"; the two cases are observationally equivalent at this horizon. They rely on other studies for the entry side: firm formation up more than 10% (Marchesi & Tang 2026) and about 20% (Bena, Bian & Giannetti 2026) in AI-compatible industries. [primary] (same)
  - Adoption context cited in the paper: 45% of employed US adults used generative AI for work by 2026Q2 (Bick, Blandin & Deming), and 24% of US employer businesses used AI in some business function by October 2026 (Census BTOS). [primary] (same)
- Skeptic angle / open questions: The AI-era test has no power to separate the authors' story from "no effect". The model's long-run sign depends on an income-effect parameter (σ): with σ=1, hours stay about 0.5% below baseline at year 15. The historical exposure measure is retrospective, not a treatment fixed before 1978. Both authors are affiliated with micro1, a company in the AI-training-data business. The paper proposes the net reinstatement ratio but does not estimate it for AI.
- Mia hook: "If displacement shows up in payroll in month one and creation shows up in year five, every 'AI isn't costing jobs' and every 'AI is killing jobs' headline is reading the wrong series. What would you measure in KvK registrations to catch the creation margin early?"

## Deep dive: Agent memory is a bet on the future. What to write down, what to forget, and "dreaming" as offline consolidation
- Why this topic, why now: Anthropic has published "The components of agent memory", its most detailed set of experiments so far on how agents should remember across sessions. Its headline finding runs against intuition: stronger models write less and forget more, and that is why they do better. Alongside it there is now a product layer (Dreams in Claude Managed Agents, plus a cookbook for building it yourself). Memory has not been a deep-dive topic before. Lucas uses it daily without having designed it: Claude Code auto memory, MEMORY.md, and this podcast's own history.md.

- Outline:
  1. **Four layers of memory, not one.** Anthropic separates (a) transcripts, the raw searchable event log; (b) memory notes the agent writes during a session; (c) structured representations such as a wiki built from those notes; and (d) injected context, a short summary loaded at the start of every session. The analogy Anthropic draws is the hippocampus, which captures experience immediately, and offline consolidation into the neocortex. The design question is which layer each fact belongs in, and what promotes it from one layer to the next.
  2. **Note-taking is prediction, and strong models predict better.** Every note is a bet that a pattern will matter again. At step 10,000 of Pokémon Red, Sonnet 3.7 had written 413 files and 977,930 characters, much of it state already visible every turn (position, money), and had one badge. Fable 5 had written 10 files and 43,406 characters of derived knowledge (strategy, tested rules, plans) and had four badges. On CL-Bench, a database task where the agent gets feedback and keeps memory across sessions, the gap memory makes grows and then levels off across model generations: Opus 4.7 0.383→0.700, Opus 5.5 0.655→0.838. What changed is the content of the notes. Older models wrote untested theories; newer ones close the loop with verified rules and "trap" warnings.
  3. **Rigid memory rules hurt strong models.** Telling Opus 5 to "record only failures" cost 0.234 in score (Opus 4.7: −0.150). Weaker models are different: Sonnet 4.6 opened its memory before answering less than half the time, and simply telling it to read memory first raised its score from 0.364 to 0.641. The policy Anthropic recommends for frontier models is simple guidance (write notes when asked or when something is clearly worth keeping) and leaving salience to the model. So the right memory instructions depend on the model; they do not carry over unchanged when the model changes.
  4. **Memory rots, so consolidate offline ("dreaming").** Notes written in the moment can be wrong, and a wrong note is worse than none. In Pokémon, a note put the Mt. Moon PokéCenter on the wrong side, and Claude fell back down the same one-way ledge three times. Dreaming re-checks notes against the transcripts between sessions, fixes them, de-duplicates, repairs links and builds a wiki. With the corrected note, Claude reached Cerulean City at action 1,935 of 3,000; with the raw note or with no memory it never got there. In the Managed Agents product, a dream takes a memory store plus 1–100 session transcripts and writes a new store. The input store is never modified, so you can review the result and discard it, which makes it a human-in-the-loop gate by construction.
  5. **A wiki complements search; it does not replace it.** On a corpus of about 350,000 internal Stainless files (about 420M tokens) with 25 questions, the wiki alone went from 13% to 48% of graded criteria as the dreaming budget grew. Search alone stayed flat at 53%. Wiki plus search rose from 54% to 61% and used about 20,000 fewer tokens per question. On a Harvey merger task needing synthesis across documents, the wiki scored 87% against 73% for search. On questions answerable from a single document there was no clear advantage. This is the RAG-versus-precomputed-synthesis trade-off: compilation pays off on multi-hop questions.
  6. **Failure modes to design against.** The first is over-abstraction: one wiki grew to 1.77 times the size of its 115 KB source, the Borges map as big as the empire. The second is concurrent writers: agents writing to a shared provisions page overwrote each other, leaving 41 of 57 facts (72%). One page per contract with verbatim quotes kept 57 of 57. The third is security: the cookbook treats transcripts as untrusted input. Analyzers get file tools only, with no shell or web access, and transcript text is read through a tool rather than placed in the prompt, so an injected instruction can at most corrupt the store, within a budget. The output store is mounted read-only for working agents. Then there is cost and staleness: Anthropic lists distraction during the task, compute for dreaming, drift as the environment changes, and memory hallucinations as open problems.

- Facts and examples with sources:
  - Four-layer taxonomy; Pokémon numbers (413 files / 977,930 chars / 1 badge vs 10 files / 43,406 chars / 4 badges); CL-Bench scores with and without memory (Opus 5.5 0.838/0.655, Sonnet 5.5 0.833/0.644, Opus 5 0.828/0.564, Opus 4.7 0.700/0.383, Sonnet 5 0.610/0.306, Sonnet 4.6 0.364/0.330); "record only failures" penalties; Sonnet 4.6 0.364→0.641; Mt. Moon case; Stainless wiki results; Harvey LAB 87% vs 73%; 72%→100% contract facts; 1.77× over-abstraction; listed limitations. [primary] (https://www.anthropic.com/research/components-of-agent-memory)
  - Quote: "For stronger models, giving them freedom to judge salience was more effective than setting fixed rules in advance, and those rules could end up weakening performance." [primary] (same)
  - Wiki growth: 103 pages / 766 links after 2 sessions, 222 pages / 12,893 links after 128 sessions. [primary] (same)
  - Dreams API: input is one memory store plus 1–100 sessions; output is a new store and the input is never modified; runs take minutes to a few hours; billed at standard token rates, scaling roughly linearly with sessions; research preview; not eligible for zero data retention except for self-hosted Managed Agents. An optional `instructions` field steers the synthesis, but line-level edit commands "generally produce no change". [primary] (https://platform.claude.com/docs/en/managed-agents/dreams)
  - Cookbook DIY version: a Sonnet 5.5 lead agent writes a workflow. Haiku 5.5 "transcript-analyzer" agents (one per transcript, up to 64 in parallel) verify and enrich memory files, then a Haiku 5.5 "memory-organizer" merges duplicates and fixes the index. Files carry YAML frontmatter, `[[slug]]` links and an `_index.md`. An example run on 11 transcripts (283 KB) cost $0.36 and took 2.5 minutes. It can run nightly from cron, and if a night fails the next run retries the same window. The store is mounted with `"access": "read_only"`. Secrets are referred to by name only. [primary] (https://platform.claude.com/cookbook/managed-agents-cma-dreaming-with-a-dynamic-workflow)
  - Claude Code auto memory: Claude writes the notes itself; per repository; the first 200 lines or 25 KB are loaded into every session. Claude treats this as context, not enforced configuration, and the docs recommend a PreToolUse hook to block an action reliably. [primary] (https://code.claude.com/docs/en/memory)
  - The Decoder notes parallel work at Google: "Dream-RSI" uses dreaming to improve agent search strategy, and "WikiSkill" keeps raw transcripts, distilled knowledge and instructions in separate layers. [secondary] (https://the-decoder.com/anthropic-says-the-key-to-agent-memory-is-knowing-what-to-forget-not-how-much-to-store/)

- Practical takeaway Lucas could apply this week:
  - Audit one memory file he already has (Claude Code MEMORY.md, a skill's notes, or this podcast's history.md) with three questions. Is anything in it re-derivable from what the agent can already see, the Sonnet 3.7 mistake? Is every rule backed by a tested instance? Does anything rely on a rigid "only record X" instruction that a current model would handle better on its own judgment?
  - Build a minimal nightly "dream" for one agent: a cheap model reads the day's transcripts as files (never in the prompt) and checks each existing note against them. It writes a new memory version beside the old one, and he looks at the diff once a week before promoting it. That gives verification, rollback and a small human role, the "acceptor" pattern from earlier episodes applied to memory.
  - For RAG over reports and papers, test a precompiled wiki layer next to the existing retriever on multi-document questions only. Anthropic's data say that is where the gain is, and that on single-document lookups it may be wasted spend.
