## Deep dive: The AI data editor — agents that reproduce, stress-test and extend published economics research

- Why this topic, why now: This week NBER put out Schwartz, Andrews and Shapiro's working paper w35782. It runs an open-source LLM workflow over 4,452 published replication packages and flags discrepancies in 3,460 articles or their appendices. In the same month, Econ Journal Watch published a critique of using chatbots to validate proofs. This is Lucas's own field (replication, coding and econometrics agents, validating AI output), and it is a clean Sunday "AI for research" topic. It also carries over yesterday's architecture lessons: isolation, sandboxing, and keeping the LLM away from the answer key. It is not on the past deep-dive list.

- Outline:
  1. **The scale shift: from replicating one paper to auditing a whole field.** Replication is expensive and badly rewarded, so it rarely happens. Kubota et al. make exactly this point and describe an iterate loop: interpret text → generate code → execute → analyse discrepancies. The NBER workflow pushes that loop to field scale. It takes each article's *published replication package* and does three things. Reproduce: rerun, compare with the published numbers, run automated sensitivity analysis. Improve: find a faster or better implementation. Extend: add an analysis the paper did not contain. The underlying mechanism is that replication packages are machine-executable artefacts. A coding agent inside a container can treat "rerun and diff" as an ordinary software task.
  2. **What "flags a discrepancy" means, and what it doesn't.** 3,460 out of 4,452 sounds like most of economics is broken. But a flag just means some reproduced number differs from the published one, possibly only in an appendix. Rounding, seeds, software versions or a typo all count. The headline needs a severity breakdown that we could not verify from the abstract (see skeptic angle). For the episode: a flag is a lead for a human editor, not a verdict.
  3. **Three regimes of reproduction, with different evidence.**
     (a) Code + data available (NBER workflow; Alizadeh et al.'s SocSci-Repro-Bench). Claude Code (Opus 4.6) gets 93.4% task-level and 78.0% paper-level accuracy. Codex (GPT-5.3) gets 62.1% and 35.8%.
     (b) Methods description + data only, no original code (Kohler et al., "Read the Paper, Write the Code"). The best configuration gets the sign right over 90% of the time and lands over 80% of reproduced values inside the original 95% CI. Most divergences can be traced to a specific root cause, and the root causes include underspecified papers, not just agent mistakes.
     (c) Pure reasoning checks on math proofs (Toda). Here chatbots endorsed flawed proofs.
     Mechanism: the more the task is "execute and compare numbers", the better agents do. The more it is "judge correctness from text", the worse they do.
  4. **The confirmation-bias trap: never hand the agent the answer key.** Alizadeh et al. show that giving agents the paper PDF raises overall accuracy slightly. But on tasks that are *not* reproducible, accuracy falls (Claude Code to 63.3%), because the model "extracts expected results" instead of diagnosing that the reproduction is impossible. Confirmatory prompt framing drops Claude Code's accuracy on non-reproducible tasks from 100% to 70%, and Codex's from 90% to 60%. Kohler et al.'s design answer is strict information isolation. The agent sees only the extracted methods, output templates and a data symlink. It never sees the original code, results or paper, and the comparison is done deterministically, cell by cell, outside the LLM. This is the same principle as yesterday's dual-LLM / CaMeL pattern: the component that judges must not be steerable by the content it judges.
  5. **Human-in-the-loop: what the controlled evidence says.** Brodeur et al. (PNAS 2026) ran a randomised experiment: 288 researchers in 103 teams, three arms. Human-only teams reproduced 94% of results, AI-assisted teams 91%, AI-led teams 37%. Human-only teams found significantly more major coding errors. Caveat: the study was preregistered in May 2024 and used ChatGPT, so it measures an older generation of models and chat-style use, not today's coding agents. Contrast this with the 2026 agent results in point 3. The honest synthesis: agents are now strong *executors*, while judging which discrepancy matters is still human work. Toda's conclusion fits: "A competent human paired with a frontier model can outperform typical referees, but chatbots alone cannot yet be trusted to validate mathematical economics."
  6. **Where this goes: the AI data editor as infrastructure.** Possible uses include pre-submission checks, refereeing support and meta-science audits (Kubota et al. list these). NBER w35782 adds "improve" (more than 10x speedups in 496 articles) and "extend" (923 aligned extensions). That last one opens a question the field hasn't answered: who is the author of an agent-generated extension, and how do you guard against an automated garden of forking paths? Dutch angle: there is a funding and institutional infrastructure for replication (NWO's earlier replication programme, the Open Science NL replication call, the Netherlands Reproducibility Network). Agentic replication could make those euros go much further.

- Practical takeaway Lucas could apply this week:
  Build a mini "AI data editor" skill and run it on one of his own past projects, or on a public replication package he knows well:
  1. Run the agent in a sandbox (container, no network beyond package mirrors), with read-only access to the replication package.
  2. Reproduce blind. The agent gets the code and data but *not* the published tables, and writes its outputs to a fixed template (CSV per table).
  3. A plain Python script, not the LLM, diffs the outputs cell by cell against the published numbers and buckets each difference: exact / rounding / within SE / sign flip.
  4. Only after that does a second agent get the diff and propose explanations and sensitivity checks, with the prompt neutral ("assess whether this result holds"), never confirmatory.
  5. Plant one deliberate bug (a wrong sample restriction) as a canary and see whether the pipeline catches it. That is his own small version of the Brodeur "major coding error" measure.
  If it works, there may be a business idea: a pre-submission reproducibility check for Dutch policy institutes and university groups, or a project proposal for an Open Science NL replication round.
