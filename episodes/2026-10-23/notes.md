## News

### 1. LiteLLM 1.107.0 shipped a credential stealer, and the entry point was a token in an agent's logs
- Why it matters for Lucas: LiteLLM is the default "one API for all models" layer in a lot of home-built RAG and agent stacks, often installed unpinned and holding every provider key in one place. And the root cause chain runs through a coding agent's output landing in logs, which is exactly the kind of leak his own tooling could have.
- Facts:
  - A malicious `litellm==1.107.0` was published on 21 October 2026; all seven wheels were live on PyPI from 11:39:51 to 13:23 UTC. Compromised Docker images were pushed to Docker Hub and GHCR under the tags `v1.107.0`, `latest`, `main-latest` and `main-stable`; Docker Hub tags were removed or repointed by 14:20 UTC. [primary] (https://docs.litellm.ai/blog/security-incident-oct-21-2026)
  - The attacker held three sets of GitHub CLI OAuth tokens, one belonging to an organisation owner, which let them disable branch protection, force-push a workflow change and point the release build at a lookalike repository, `Berri-AI/litellm` instead of `BerriAI/litellm`. A third credential was used to delete workflow records afterwards. [primary] (https://docs.litellm.ai/blog/security-incident-oct-21-2026)
  - LiteLLM names three contributing causes: release permissions temporarily expanded on Monday so two engineers could publish daily bugfix backports; "Claude Code will embed a user's GitHub CLI OAuth token into a response body, and in situations where response bodies are logged, these tokens may appear in LiteLLM logs"; and an "unexpected, innocuously named user account" in an internal LiteLLM deployment exposed to the public internet. This is LiteLLM's own account of the cause. [primary] (https://docs.litellm.ai/blog/security-incident-oct-21-2026)
  - The payload: files `cook.pth`, `cook.py` and `sitecustomize.py` plus a detached Python daemon holding `/tmp/remote_code_loader.lock`; it "steals credentials and loads remote-code execution tools". [primary] (https://docs.litellm.ai/blog/security-incident-oct-21-2026)
  - The .pth and sitecustomize mechanism means the code runs on every Python start, not only when LiteLLM is imported; security firms report it collects SSH keys, cloud credentials, CI/CD secrets, AI tool tokens, browser passwords and the LLM provider keys stored in a LiteLLM proxy database. [secondary] (https://www.stepsecurity.io/blog/litellm-1-107-0-compromised-pypi-backdoored-wheels-credential-stealer) (https://www.mend.io/blog/litellm-1-107-0-compromised/)
  - Required actions per LiteLLM: delete the three files and their bytecode from site-packages, kill the daemon, pin `litellm==1.106.2`, rotate instance IAM roles, every provider key stored in the proxy DB, database passwords and all environment secrets, and check CloudTrail for `GetCallerIdentity` calls from the instance role. Enterprise customers using the private registry were not affected. [primary] (https://docs.litellm.ai/blog/security-incident-oct-21-2026)
  - LiteLLM says it had hardened its pipeline after an earlier incident in March, and that these controls were undermined by the temporary permission expansion and the token exposure. [primary] (https://docs.litellm.ai/blog/security-incident-oct-21-2026)
  - Context, the "Black October" wave of the same 48 hours: an unauthenticated RCE in PHP (PHP2Shell), a CVSS 10 GitLab flaw affecting releases since 2014 (patched in 19.5.1), Railway telling users to rotate secrets, Zeabur shutting down after 321,810 accounts were breached; Latent Space cites a claim that monthly CVEs rose from about 4k to about 15k since April. [secondary] (https://latent.space/p/ainews-black-october/)
- Skeptic angle / open questions: The Claude Code token-in-response-body explanation comes from LiteLLM's write-up; Anthropic has not been quoted on it in what I found, so present it as LiteLLM's account. The deeper lesson is not "LiteLLM is bad" but that three individually small lapses (temporary privilege, secrets in logs, an exposed internal service) compounded. Watch whether PyPI-side defences (trusted publishing, attestations) would have caught a build from a lookalike repo.
- Mia hook: "I grep'd my own agent logs after reading this and found a bearer token in a tool-call transcript. How many of us log full request/response bodies 'for debugging' and never look again?" Also: who here pins LiteLLM, and who just has `pip install litellm` in a Dockerfile?

### 2. Anthropic: Claude wrote 180 million lines of machine-checked proofs for 123 open-source libraries
- Why it matters for Lucas: It is the defensive mirror image of Black October, and a concrete answer to his standing question of how to validate AI-produced output: don't trust the model, make it produce an artefact a mechanical checker accepts. The same "verifier, not opinion" logic applies to research code.
- Facts:
  - Published 22 October 2026 by Anthropic's Frontier Red Team. [primary] (https://www.anthropic.com/research/formal-verification)
  - "Claude successfully patched the bugs it found and then proved that there are no crashes on any input (up to 64 MB) for 239 entry points across 123 different OSS-Fuzz libraries." [primary] (https://www.anthropic.com/research/formal-verification)
  - The proofs are about 180 million lines of Rocq, with a typical proof running to about 600,000 lines. [primary] (https://www.anthropic.com/research/formal-verification)
  - The proofs cover single-threaded binaries on RISC-V/Linux semantics, not the x86/ARM builds people actually deploy. [primary] (https://www.anthropic.com/research/formal-verification)
  - Bugs found that fuzzing had missed include an out-of-bounds write triggered only by 20 MB inputs, an out-of-bounds read in an image decoder that needed a 64 MB input, and a rediscovery of CVE-2026-56132 in libexpat, which needed deeply nested input. [primary] (https://www.anthropic.com/research/formal-verification)
  - "Opus 5.5 proves half of them with about 40% fewer tokens than Opus 5." [primary] (https://www.anthropic.com/research/formal-verification)
  - Anthropic's own caveat: "formally verified" does not mean bug-free; "a proof checker can't tell you whether your spec matches reality." [primary] (https://www.anthropic.com/research/formal-verification)
  - Released: a subset of the proofs on GitHub and a Claude skill from Theorem for developers to verify their own code. [primary] (https://www.anthropic.com/research/formal-verification)
- Skeptic angle / open questions: "No crashes" is a narrow property; logic errors, wrong outputs and concurrency bugs are outside it. The weak point moves from the code to the spec and the machine model, and specs are written or at least shaped by the same model. 600,000-line proofs are not human-reviewable; trust rests entirely on the Rocq kernel and the semantics. Cost in tokens per proof is not the headline, which matters for anyone wanting to copy this.
- Mia hook: "Could I do the econ version of this: have an agent prove properties of my estimation code, like 'the weights always sum to one' or 'no silent NaN propagation', instead of writing more unit tests?"

### 4. "Saving for the Machines": AI's binding constraint may be savings, and that pushes real rates way up
- Why it matters for Lucas: This is a macro model he can actually take apart (task framework, Euler equation, calibration), with a direct Dutch/European angle: if world real rates rise for an AI build-out that happens mostly elsewhere, high-debt "bystander" economies pay the bill.
- Facts:
  - Jesús Fernández-Villaverde (University of Pennsylvania, CEPR, NBER), paper dated 20 October 2026. It combines the Acemoglu-Restrepo task framework with a representative household that saves optimally, calibrated to the US, with every task becoming automatable between 2025 and 2045; closed economy, deterministic. [primary] (https://www.sas.upenn.edu/~jesusfv/Saving_Machines.pdf)
  - Headline: holding the automation path fixed, the economy grows 11.7% a year when tasks are highly complementary and households save optimally, but only 2.2% if the saving rate stays at the calibrated 2025 rate of 23%. "Slow growth might reflect too little capital accumulation instead of a technological bottleneck." [primary] (https://www.sas.upenn.edu/~jesusfv/Saving_Machines.pdf)
  - Mechanism: the saving rate equals the capital share times investment over capital income. With optimal saving that second ratio barely moves (0.69 to about 0.55 while the return climbs from 11% to 52%), so as automation pushes the capital share from one-third to one, the saving rate rises. US data has kept that ratio between 0.50 and 0.78 since 1950. [primary] (https://www.sas.upenn.edu/~jesusfv/Saving_Machines.pdf)
  - Asset prices: the short rate does not move on impact, but the ten-year real yield jumps from 5.1% to 13.6% with unit task elasticity (sigma = 1) and to 9.3% with sigma = 0.2; the thirty-year yield to 33.0% and 19.6%. High rates cut the value of the labour force ("human wealth") by two-thirds on impact. [primary] (https://www.sas.upenn.edu/~jesusfv/Saving_Machines.pdf)
  - Distribution: hand-to-mouth households lose the equivalent of 40% to 65% of consumption; the transfer that keeps their labour income on trend peaks at 4% of GDP (sigma = 1) or 20% (sigma = 0.2) and is below 4% by 2055. [primary] (https://www.sas.upenn.edu/~jesusfv/Saving_Machines.pdf)
  - The author's warning: "all my exercises are benchmarks, not forecasts"; he shares the reasons given by Imas and Moll (2026) for why growth above 15% may not materialise. [primary] (https://www.sas.upenn.edu/~jesusfv/Saving_Machines.pdf)
  - The paper's acknowledgement says he used Claude and ChatGPT for help with the proofs of the mathematical results, coding and debugging, figures, and grammar. [primary] (https://www.sas.upenn.edu/~jesusfv/Saving_Machines.pdf)
  - In a follow-up back-of-the-envelope calculation (not the closed-economy paper), he takes a government with debt at 100% of GDP and a balanced primary budget. A "bystander" (his example: Spain) pays the world rate but keeps growing at 1.6%: its debt doubles by 2033 and triples by 2035, and it needs a primary surplus of 11% of GDP in 2030, 26% in 2035 and 44% forever with unit elasticity. Its options: "default, inflation, or, most likely, financial repression: capital controls that keep domestic savers from investing in machines abroad." [secondary] (https://marginalrevolution.com/marginalrevolution/2026/10/will-bystander-economies-be-able-to-finance-their-governments.html)
  - Even the adopter (US) sees debt reach 296% of GDP in 2040 under unit elasticity, but has a way out: a 36% tax on net capital income holds debt at 100% of GDP in the limit (20% with strong complementarity). [secondary] (https://marginalrevolution.com/marginalrevolution/2026/10/will-bystander-economies-be-able-to-finance-their-governments.html)
- Skeptic angle / open questions: Everything is conditional on full automation by 2045, which is an assumption, not a finding. Representative-agent optimal saving is the polar case that maximises the saving response; the fixed-rate case is the other pole, and the truth (heterogeneous households, financial frictions) sits in between, as he says himself. The fiscal exercise assumes zero adoption by the bystander and an integrated capital market, deliberately extreme. Test against data: are long real yields actually pricing anything like this? The paper cites Chow et al. (2025) on using long rates to infer AI expectations.
- Mia hook: "As an economist, the bit that bugs me: the Netherlands is a big net saver with huge pension funds. In his world, does a country like that win as an owner of other people's machines rather than lose as a bystander?"

## Deep dive: Where should an agent's secrets live? Sandboxes, egress proxies and credential brokering

- Why this topic, why now: The LiteLLM compromise is a textbook case of the problem: secrets sat where code could read them (environment, files, logs), and a piece of code that runs on every Python start harvested them. In the same 24 hours, NVIDIA released OpenShell, an open-source runtime for agent fleets built around "agents never see real credentials", and Google detailed Agent Compute Engine, where each agent gets a microVM with no network card and no secrets inside. Claude Code's own sandbox now supports credential masking with placeholder values. This is Lucas's top interest (autonomous agents that are safe), and it differs from the past deep dives: the 3 October episode covered prompt-injection defence by architecture (what the model is allowed to decide); this one covers the runtime layer (what the process can physically touch and send).

- Outline:
  1. **The threat model shifts from "bad output" to "bad process".** Whether the cause is a prompt injection, a poisoned dependency (cook.pth) or a model making a mistake, the result is the same: arbitrary code runs with the agent's privileges. Two questions then decide the damage: what can that process *read* (files, env vars, metadata endpoints, logs), and where can it *send* things (egress)? The LiteLLM chain shows that a secret anywhere readable (a log containing a token) is a secret exfiltrated eventually. The 9 October AgentCorruption story (IMDS credential theft) was the same pattern.
  2. **Isolation tiers: what each boundary actually stops.** (a) OS-level process sandboxes: Seatbelt on macOS, bubblewrap on Linux (Claude Code), Landlock + seccomp (OpenShell). Cheap and fast, same kernel as the host, so a kernel bug is a shared escape route. (b) Containers: namespaces and cgroups, again a shared kernel; gVisor puts a user-space kernel in between (Modal's original sandbox primitive). (c) MicroVMs (Firecracker-style, Google ACE): own kernel, hardware virtualisation, strongest separation, historically slow to start, which is what snapshotting is now fixing. Mechanism to stress: the boundary only protects what is *outside* it. Claude Code's Bash sandbox wraps shell commands, but file tools, MCP servers and hooks run outside with full access.
  3. **Egress is the real control.** Every tier above leaks data if the network is open. The common design is: no direct route out, all traffic forced through a proxy that checks destination (and sometimes method/path) against an allowlist. Claude Code: no direct route, a local proxy checks each host against allowed domains, which start empty. OpenShell goes further: seccomp intercepts TCP opens and DNS queries, identifies the calling binary from trusted `/proc` data, and policy can reference HTTP methods and API calls (per-binary, L7). Google ACE removes the network interface entirely: all traffic crosses a virtio-vsock channel to an unprivileged mediation proxy, then an external proxy and gateway that validates request scopes.
  4. **Credential brokering: the agent holds a placeholder, the proxy holds the key.** If the proxy sits on every outbound path anyway, it can inject secrets on the wire, only for approved destinations. The process never holds the real value, so stealing env vars or files yields a useless sentinel. Claude Code's "mask" mode: sandboxed commands see a per-session sentinel; the proxy substitutes the real value on requests to `injectHosts`. This requires TLS termination at the proxy (it must see request contents), and AWS SigV4 needs re-signing because the signature covers the content. OpenShell: the supervisor holds provider credentials and injects them only into approved requests. Google ACE: "zero persistent secrets" in the guest, no metadata server access, a short-lived SPIFFE workload identity that is useless if exfiltrated, with long-lived user credentials swapped in "in flight" at the gateway. Trade-off: the proxy becomes a high-value target and a TLS man-in-the-middle by design; and an allowed host can still be an exfiltration channel (send the data, not the key).
  5. **Policy as reviewable code, and who approves widening.** Static allowlists rot, so agents ask for more. OpenShell keeps filesystem and process rules locked at sandbox creation, makes network and credential rules hot-reloadable, and runs a formal "policy prover" that flags new credentialed reach, new HTTP methods or cloud-metadata access, which blocks auto-approval and forces human review. Claude Code splits trust by settings scope: masking, TLS termination and turning off filesystem isolation are honoured only from user/managed settings, never from a repository's `.claude/settings.json`, so a cloned repo can't widen its own sandbox. Its escape hatch (`dangerouslyDisableSandbox` retry after a failure) can be disabled with `allowUnsandboxedCommands: false`, and `failIfUnavailable` stops it silently running unsandboxed.
  6. **Speed makes strict isolation affordable.** The old excuse for weak isolation was latency and cost. Snapshot-and-fork changes that: Google ACE maps a snapshot into memory with copy-on-write so microVMs on a host share base pages and only allocate their private delta, and detects the "thinking" phase to scale idle agents to near-zero. Modal's CEO describes the same direction: sandboxes that wake for a command and snapshot back to sleep, one per command, forking for parallel work. When a fresh VM per task costs about as much as a container, "ephemeral and secret-free by default" stops being a luxury.

- Facts and examples with sources:
  - Claude Code's sandbox covers Bash, PowerShell and Monitor commands and their children; built-in file and web tools, hooks, local MCP servers and helpers like `apiKeyHelper` run outside it with full access. [primary] (https://code.claude.com/docs/en/sandboxing)
  - It runs on macOS (Seatbelt), Linux and WSL2 (bubblewrap + socat); "On native Windows, Claude Code runs commands unsandboxed." It is off by default. [primary] (https://code.claude.com/docs/en/sandboxing)
  - Default reads include "most of the machine, including credential files such as `~/.ssh` and `~/.aws/credentials`"; environment variables, including secrets, are inherited unless configured. "There is no built-in credential deny list." [primary] (https://code.claude.com/docs/en/sandboxing)
  - Network default: no direct route out; a local proxy checks each host against allowed domains, which start empty. [primary] (https://code.claude.com/docs/en/sandboxing)
  - Masking: sandboxed commands see a per-session sentinel and the proxy substitutes the real value on outbound requests to allowed hosts; requires `network.tlsTerminate`; mask entries are ignored in a repository's settings files. On macOS a masked file is blocked rather than replaced by a sentinel copy. [primary] (https://code.claude.com/docs/en/sandboxing)
  - If the sandbox can't start, Claude Code by default runs commands unsandboxed; `sandbox.failIfUnavailable: true` makes it exit instead. [primary] (https://code.claude.com/docs/en/sandboxing)
  - Anthropic's guidance: always run `--dangerously-skip-permissions` sessions inside a container, VM or the sandbox runtime, because the Bash sandbox alone "is not sufficient for fully unattended runs"; for untrusted repositories, a dedicated VM. The sandbox runtime (`srt`, a beta research preview) wraps the whole Claude Code process, including MCP servers and hooks, and by default denies writes to `.git/hooks`, `.mcp.json`, `.claude/commands`, `.claude/agents` and shell startup files. [primary] (https://code.claude.com/docs/en/sandbox-environments)
  - Anthropic's own warning: "Any approach that allows network egress can still leak data the agent can read." [primary] (https://code.claude.com/docs/en/sandbox-environments)
  - NVIDIA OpenShell: Apache 2.0; gateway, supervisor (trusted side) and sandbox (untrusted agent); compute drivers for Docker/Podman (Unix socket), Kubernetes (mTLS) and microVM (vsock); Landlock for filesystem, seccomp for process and network interception; declarative YAML policy; SDKs in Python, TypeScript, Go and Rust; runs on Linux, macOS on Apple Silicon and Windows via WSL 2. [primary] (https://github.com/NVIDIA/OpenShell) (https://docs.nvidia.com/openshell/latest/about/architecture.html)
  - OpenShell's policy prover flags new credentialed reach, new HTTP methods and cloud-metadata access, and these findings block auto-approval. [primary] (https://docs.nvidia.com/openshell/latest/about/architecture.html)
  - Google Agent Compute Engine: a hardware-isolated microVM per agent, Titanium IPU; microVMs "lack standard virtual network interfaces, default IP gateways, or direct VPC access"; traffic goes over virtio-vsock to a mediation proxy; guests hold "zero persistent secrets" and have no metadata-server access; SPIFFE-based workload identity "not usable to call a backend API directly, if it is exfiltrated"; snapshot once and "fork it into thousands of memory-deduplicated copies". Targeted for preview "in the coming months"; no pricing given. [primary] (https://cloud.google.com/blog/topics/ai-infrastructure/agent-compute-engine-deep-dive)
  - The Decoder reports suspend and resume under 500 milliseconds in a 200,000-agent test. [secondary] (https://the-decoder.com/googles-agent-compute-engine-gives-every-gemini-agent-its-own-hardware-isolated-micro-virtual-machine/)
  - Modal's CEO Erik Bernhardsson: Modal built sandboxes on gVisor and now also offers full VMs because some uses need full Linux compatibility; he sees the future as sandboxes that start in about 100 ms, run a few commands and snapshot, with forking for parallel agents; after the Hugging Face incident (an exploited app hosted on Modal used as a springboard) Modal is exploring more restrictive defaults, citing how S3 made public buckets harder. [primary] (https://www.youtube.com/watch?v=IiZ9yd2Do8I)
  - Modal reports nearly three billion sandboxes spun up and over $1 billion annualised run rate. [secondary] (https://latent.space/p/modal-d/)

- Practical takeaway Lucas could apply this week:
  1. Since he works on Windows, Claude Code's Bash sandbox does nothing on the native host. Move unattended agent work into WSL2 or a dev container, set `sandbox.enabled: true`, `allowUnsandboxedCommands: false` and `failIfUnavailable: true` in user settings.
  2. Add a `sandbox.credentials` block: `deny` for `~/.ssh` and cloud credential files, `mask` with `injectHosts` for the API keys his RAG tools need (for example the model provider key only to the provider's API host).
  3. Audit logging in his own tools: grep logs and agent transcripts for `ghp_`, `gho_`, `sk-`, `Bearer`. Stop logging full request/response bodies, or redact them.
  4. Pin LLM gateway dependencies (LiteLLM and similar) by version and hash, and check whether any environment installed `litellm==1.107.0` on 21 October.
