GEORGE: Exactly. MIA: And LiteLLM shows the read side is bigger than people think. That token wasn't in a vault. It was in a log.

MIA: Okay, isolation tiers. I know the names. I want to know what each one actually stops.
GEORGE: Three tiers. Cheapest is an OS-level process sandbox. Seatbelt on macOS, bubblewrap on Linux, which is what Claude Code uses, or Landlock plus seccomp, which is what OpenShell uses. MIA: And containers are the same story with better packaging.
GEORGE: Pretty much. Namespaces and cgroups, still one shared kernel. gVisor puts a user-space kernel in between, which is what Modal originally built its sandboxes on. MIA: Fine, but the rooms only matter if the right things are in them.
GEORGE: That's the mechanism I'd stress most: a boundary only constrains what's inside it. Claude Code is a good example. Its sandbox covers Bash, PowerShell and Monitor commands and their children. MIA: Why those specifically?
GEORGE: Because they're all places where a write today becomes execution later, often outside the sandbox. It's the sitecustomize trick in another costume. A git hook runs the next time you commit, a shell startup file the next time you open a terminal.
MIA: Okay. But all of that is containment. If the network is open, none of it matters much.

In Claude Code, a local proxy checks each host against allowed domains, and that list starts empty.
MIA: And the others?
GEORGE: OpenShell goes finer. MIA: Here's my problem with allowlists. Allowing api dot github dot com sounds safe, until you remember an agent can open a public gist on it. How do you stop exfiltration through a host you have to allow?
GEORGE: With a domain allowlist, you can't. That's the honest answer. Method and path rules help: you can allow reading issues without allowing writes to gists, which is the kind of thing OpenShell's request-level policy is for. But any host you allow to receive data can carry data. So the other half of the defence is shrinking what the agent can read in the first place. Which brings us to the bit I find most elegant.
MIA: Credential brokering.
GEORGE: Yes. If the proxy sits on every outbound path anyway, it can be the thing that holds the key. The agent holds a placeholder, the proxy swaps in the real secret on the wire, and only for approved destinations. Like a cloakroom: the agent carries the ticket, never the coat. Steal its environment variables and you get a useless sentinel.
MIA: How does Claude Code do it?
GEORGE: There's a mask mode. Sandboxed commands see a per-session sentinel value, and the proxy substitutes the real value on outbound requests to the hosts you list under injectHosts. Two mechanical consequences. It requires TLS termination at the proxy, the network dot tlsTerminate setting, because the proxy has to see inside the request to replace the value. And AWS signatures need re-signing, because SigV4 signs over the request contents, so swapping a value breaks the signature. One platform quirk: on macOS a masked file is blocked rather than replaced with a sentinel copy.
MIA: And OpenShell?
GEORGE: Its trusted side, the supervisor, holds the provider credentials and injects them only into approved requests. Google goes furthest: "zero persistent secrets" in the guest, no metadata server access, and a short-lived workload identity based on SPIFFE that is, quote, "not usable to call a backend API directly, if it is exfiltrated." Long-lived user credentials get swapped in flight at the gateway.
MIA: Okay, my honest first reaction when I turned masking on: great, now my proxy is a man-in-the-middle holding every key I own. Is that better, or just a different single point of failure?

MIA: Which is funny, because a LiteLLM proxy is kind of a credential broker already. Every key in one place.
