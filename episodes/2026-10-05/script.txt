GEORGE: Right. It's called RRSI, from Google Cloud AI Research together with UNC-Chapel Hill, Stanford and Wash U. Peng Xia, Rujun Han, Zifeng Wang, Chen-Yu Lee and others, version two dated the twenty-third of September, and the code is public. Let me set it up. An agent is a frozen model, the policy, plus a harness. The harness is everything around it: system and task prompts, control flow, meaning when to plan, act, reflect or stop, tool interfaces, memory and skill files, and context management.
MIA: The operating system around the model.
GEORGE: Exactly. Harness evolution keeps the weights fixed and runs a loop. Run the harness on an evolve set of tasks, summarise the failures, let a proposer model draft edited harnesses, score them on the same evolve set, keep the best, repeat.
MIA: Which is what I do by hand every week with my skills. Tweak, run, check, keep.
GEORGE: And what everyone is starting to automate. Recursive self-improvement at the system level, with no new weights.
MIA: So why does it overfit? I get it intuitively, but say it properly.
GEORGE: Adaptive reuse of a finite test set. Each round's proposals depend on scores from the same tasks in earlier rounds, so the test set slowly stops being a test set. It's what Dwork and colleagues formalised in twenty fifteen as adaptive data analysis.
MIA: The garden of forking paths. Specification search. Every economist knows it: run enough regressions on the same data and something comes out significant.
GEORGE: You know that world better than I do. The paper names three channels. Benchmark-specific fitting, where the proposer hardcodes facts about particular tasks. Noise chasing: agent runs are stochastic, so some candidates win by luck and get kept. And complexity accumulation, where the gains come from more retries and more tokens rather than better mechanisms.
MIA: How big is that in practice?
GEORGE: There's an independent study by Ding and colleagues, "What evolves when we talk about harness evolution?" They split evolved gains into overfitting, test-time scaling and generalisable improvement. Overfitting accounts for ninety-eight percent of the gains on ALFWorld and seventy-nine percent on LiveMath. On CREATE, seventy-three percent is test-time scaling, so just spending more compute. On SWE-bench Verified, overfitting is only fifteen percent. And in four of sixteen settings, the evolved harness did worse than baseline on held-out data.
MIA: Worse than doing nothing at all.
GEORGE: My favourite example: on LiveMath, the phrase "a stronger result can be proven" appeared in twenty-one of thirty-five training questions, and it was always correct. Evolution found that artefact and exploited it.

MIA: So what does the paper actually do about it?
GEORGE: Two sides. Limit how much the search can fit in each round, and then control which gains get to become permanent. Proposal side first. An annealed edit budget: the number of independently attributable edits per candidate follows a cosine schedule, from three or four at the start down to one.
MIA: Why allow bundles early on?
GEORGE: Because some mechanisms need coordinated changes. A new verification step plus the instruction telling the model when to use it. Early rounds are for discovering mechanisms. Late rounds are single, attributable edits, so you know what moved the score. It acts like an L-zero constraint on the update: you limit how many things change, not how much.
MIA: Annealed like a learning rate. Nice.
GEORGE: Second, evidence-aware credit assignment. Every edit is logged with its component, its hypothesis, the diff, the change in score, the change in cost and whether it was accepted. Falsified hypotheses stay in the log as negative evidence, so the search doesn't keep retesting the same bad idea.
MIA: That's a lab notebook. Honestly, half the waste in my own tuning is retrying something I already rejected three weeks ago.
GEORGE: Third, structured exploration. If progress over three rounds stays within the noise band, a reserved proposal slot goes to component types that haven't been tried yet: prompt, control flow, config, output plumbing, context management, client tool, skill, memory, subagent.
MIA: Because otherwise everything ends up being a prompt edit.
GEORGE: Prompts are the cheapest thing to change, so the proposer gravitates there. Then the selection side, which I think is the cleverer half. First, a leakage critic. It reads each diff before evaluation and rejects edits that encode task names, entities, values, answers or benchmark-specific logic.
MIA: Does it matter that it's before evaluation?
GEORGE: A lot. If you screened after scoring, the leaky candidate would already have its inflated score, and later rounds would be drawn towards it. Screening first means it never gets the score that attracts the search.
MIA: Like keeping a contaminated regression out of the results table entirely, instead of footnoting it.
GEORGE: Exactly. Second, a noise-adjusted floor. You run the unchanged base harness repeatedly to estimate the noise band, delta. Then a candidate needs a score of at least the best so far minus delta.
MIA: Minus? So slightly worse candidates can get through.
GEORGE: Within the noise, yes, and that's deliberate, for candidates that save cost or add structure. But the floor is anchored to the best so far, so the search can't walk downhill through a chain of regressions that each look harmless on their own.

GEORGE: Structural pruning. Components with no positive measured gain over the pruning window are handed to the proposer as deletion targets. The harness has to be able to shrink, not just grow.
